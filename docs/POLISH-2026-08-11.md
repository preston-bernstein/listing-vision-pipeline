## Applied — MUST

- **`packages/core/src/alert/sendAlert.ts`** — a live Telegram send never checked
  `response.ok` and had no error handling at all; worse, the `alerts` DB row and the output
  JSON file were written *before* the fetch, so a failed send was invisible (no log, no
  thrown error) and permanently unretryable (the idempotency check would skip it on every
  future run). Fixed: the fetch now runs first, `response.ok` is checked, and a failure
  throws before anything is persisted — a failed send stays eligible for retry. Added a
  regression test (`alert.test.ts`, "with liveSend true and a non-ok Telegram response...").
  `cli/alert.ts`'s `processOneCandidate` now catches this per-candidate so one failed send
  doesn't abort the rest of the alert run.

## Applied — SHOULD

- **Consolidated `SOURCES`** (the three listing-source names), previously declared
  independently in 5 places (`db/schema.ts`, `schema/normalized.ts`, `normalize.ts`,
  `ingest/index.ts` ×2) down to one canonical declaration in `schema/normalized.ts`,
  imported everywhere else. The DB `CHECK` constraint's raw SQL literal was left as literal
  text (with a comment tying it back to `SOURCES`) rather than risk changing drizzle's
  migration-generation behavior.
- **Consolidated `DEFAULT_FIXTURES_ROOT`** (`<repo root>/fixtures`), previously re-derived
  independently via `import.meta.url` path math in 5 places, each with a hand-maintained
  "N levels up" comment. Now one shared module, `packages/core/src/fixturesRoot.ts`.
- **Consolidated 4 DB-handle type names** (`RankDb`, `ScoreDb`, `Db`, `AlertDb` — three
  different derivations for the same concept) into one `AppDb` type,
  `packages/core/src/db/types.ts`.
- **Deleted dead speculative generality** in `normalize.ts`: a `SourceRecord` union type, a
  4th function overload, and the runtime branch dispatching on it — added "so a future
  caller could use it," never adopted by anything except its own test (deleted alongside it).
- **Deleted a duplicate CLI entry point**: `ingest/index.ts` had a second, "directly
  runnable" `if (import.meta.url === ...)` block duplicating `cli/ingest.ts`, and it was the
  *only* place implementing the `--out <file>` flag that `plan.md` specs for the `ingest`
  CLI. Removed the duplicate, moved `--out` into `cli/ingest.ts` where it belongs.
- **Fixed `cli/rank.ts`**: it was the only one of the four CLI wrappers that didn't validate
  `DATABASE_URL` before importing `db/client.js` — an unset/bad `DATABASE_URL` silently
  created a stray SQLite file instead of failing fast. Brought in line with
  `cli/score.ts`/`cli/alert.ts`'s existing validate-then-dynamic-import pattern.
- **Standardized CLI exit handling**: the four `main().catch()` handlers were split between
  `process.exitCode = 1` (safe — lets buffered output flush) and `process.exit(1)` (hard
  terminate). Standardized on `process.exitCode = 1` everywhere. (Synchronous fail-fast
  `process.exit(1)` calls inside env-validation helpers were left as-is — a different,
  legitimate pattern.)
- **Added per-item resilience** in `cli/score.ts`'s `scoreAllRecords` (one failed vision call
  no longer aborts the batch) and `cli/alert.ts`'s candidate loop, mirroring the pattern
  `ingest/index.ts`'s `runIngest` already used.
- **`cli/score.ts`**: renamed `requireEnv()` → `validateEnv()` and changed its return type to
  `void` — the returned config object was silently discarded by its only caller.
- **`dashboard/server/index.ts`**: the image-read catch block returned 404 with zero log
  trail, unlike every other catch block in the repo. Added a `console.error` before the
  response so a permission error or other non-ENOENT failure is distinguishable from a
  genuinely missing fixture during debugging.

## Escalated — not applied

- **`packages/dashboard/server/index.ts` reaches into `packages/core`'s internals via deep
  relative paths** (`../../core/src/db/client.js`), while `core/package.json` declares
  `exports`/`main`/`types` → `./dist/index.js` — but `core` has no `build` script and no
  `dist/` exists, so that declared public entry point is fictional. Two ways to resolve, both
  changing the package boundary contract: (a) add a `src/index.ts` barrel + build step to
  `core` and have `dashboard` depend on it by package name, or (b) accept the existing deep
  relative-import coupling and delete the misleading `exports`/`main`/`types`/`files` fields
  from `core/package.json`. This is a real architecture decision, not a mechanical fix —
  flagging for your call rather than picking one.

## Regression safety net

`npm run lint`, `npm run typecheck`, and `npm run test` (58 core tests + 26 dashboard tests)
all pass after every change above. A dedicated correctness-focused review agent (opus) was
run against the full diff afterward, specifically targeting the highest-risk change (the
`sendAlert` reordering) and the cross-cutting consolidations, and found — then this pass
fixed — four real regressions before commit:

- **[MUST]** `cli/score.ts`'s new per-record resilience (item above) tracked a `failedCount`
  but never surfaced it as a non-zero exit code — a total vision-endpoint outage now silently
  exited 0 instead of 1. Empirically confirmed both broken and fixed (`score: done — ...
  failed 9 listing(s)` now exits 1, matching the pre-polish behavior for a total failure).
- **[SHOULD]** Same class of bug in `cli/alert.ts`'s candidate loop — fixed the same way
  (`process.exitCode = 1` when `failed > 0`).
- **[SHOULD]** The `sendAlert` reorder (fetch-then-persist) closes the original "row written,
  send lost" gap but opens the inverse one: if the Telegram POST succeeds and the subsequent
  file/DB write then fails, the message was delivered but nothing was persisted, so the next
  run's idempotency check won't see it and will re-send. This is inherent to the reorder, not
  fully fixable without a distributed transaction — made loud instead: a dedicated log line
  now flags this specific failure mode by name so it's never silent.
- **[SHOULD]** `cli/rank.ts`'s new `DATABASE_URL` requirement (item above, matching the other
  three CLI stages) was correct behavior but exposed a pre-existing README gap: nothing in the
  repo auto-loads `.env`, so `cp .env.example .env` alone was never sufficient for the
  documented "Running the pipeline" quick-start — it just hadn't been hit at the `rank` stage
  before. Fixed the README to instruct exporting `.env` into the shell
  (`set -a; source .env; set +a`) and clarified the `DATABASE_URL` config table row.

`fallow`'s dead-code/duplication/health signal is unchanged (still 0/0/90-A) confirming the
consolidations didn't introduce new mechanical issues. Full suite re-run clean after all four
fixes above.

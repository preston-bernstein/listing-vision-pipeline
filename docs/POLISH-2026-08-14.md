## Applied — MUST

- **`packages/core/src/db/client.ts` — DATABASE_URL resolved against the wrong directory.**
  A relative `DATABASE_URL` (e.g. the `.env.example` default, `file:./data/app.db`) was
  resolved against `process.cwd()`, and npm workspace scripts run with cwd set to the invoked
  package's directory. So `npm run score -w core` wrote to `packages/core/data/app.db`, while
  `npm run dev:server -w dashboard` opened a *different, empty* `packages/dashboard/data/app.db`
  — the dashboard would silently render an empty table with no error, exactly matching the
  documented "Running the pipeline" quick-start in the README. Every test masked this
  (`playwright.config.ts` and `e2e/global-setup.ts` both force an absolute path). Fixed by
  resolving a relative `DATABASE_URL` against the repo root, using the same
  `import.meta.url`-derived idiom `fixturesRoot.ts` already uses for the same class of bug.
  Verified empirically: opened the DB from both `packages/core` and `packages/dashboard` as
  cwd with a relative `DATABASE_URL` and confirmed both now resolve to the same file at the
  repo root.

  **Self-caught regression during this fix**: the first version of this fix resolved *every*
  non-absolute `DATABASE_URL` against the repo root, including `node:sqlite`'s special
  `":memory:"` location (used by `server.test.ts` for a real in-memory DB) — turning it into
  an ordinary path and defeating the in-memory semantics, which silently created real files
  named `:memory:`/`:memory:-shm`/`:memory:-wal` on disk during `npm test`. Caught this via
  the stray files appearing in `git status` after running the suite, and added a guard
  (`SPECIAL_SQLITE_LOCATIONS`) so `":memory:"` and `""` pass through unresolved. Re-verified
  the full suite runs clean afterward with no stray files.

- **`packages/dashboard/tsconfig.json` — the entire React client was silently unchecked.**
  `include` was `["src/**/*", "server/**/*"]`, but the actual client source lives at
  `client/src/`, not `src/` (that directory doesn't exist). `tsc --noEmit -w dashboard` was
  therefore only ever checking `server/index.ts` (plus its core imports) — `App.tsx` and
  `main.tsx` were never type-checked by the `typecheck` script, `npm run lint`, or CI, only by
  whatever `vite`/`vitest` do at runtime (neither type-checks). Confirmed by running
  `tsc --listFilesOnly` before and after the fix. Fixing the glob to `client/src/**/*`
  immediately surfaced a real latent bug: `main.tsx`'s `import App from './App'` was missing
  the `.js` extension required under this repo's `NodeNext` module resolution — fixed
  alongside the config.

## Applied — SHOULD

- **Re-fragmented `SOURCES` import surface, fixed.** The 2026-08-11 pass consolidated the
  `SOURCES` *declaration* into `schema/normalized.ts`, but `db/schema.ts` then re-exported it,
  so consumers split down the middle (`rank.ts` and the dashboard server imported it from
  `db/schema.js`; `ingest/index.ts` and `normalize.ts` imported it from `schema/normalized.js`).
  Dropped the re-export; both remaining consumers now import directly from the canonical module.
- **Consolidated the `Source`/`SourceName` type** — three independent declarations
  (`normalize.ts`'s `Source`, `ingest/index.ts`'s `SourceName`, `rank.ts`'s inline
  `(typeof SOURCES)[number]`) for the same concept, down to one exported `Source` type in
  `schema/normalized.ts`, next to `SOURCES` itself. Same defect class the prior pass fixed for
  the DB-handle types; this one was missed.
- **`rank.ts` now exports `RANK_LIMIT_BOUNDS`** (`{ min: 1, max: 1000, default: 50 }`); the
  dashboard server's `listingsQuerySchema` derives its bounds from it instead of a copy-pasted
  `1`/`1000`/`50`. The double-validation itself is intentional (an existing code comment
  explains: the server validates first so it can return a clean 400 instead of an uncaught
  `ZodError`) — only the duplicated literals were fixed, not the validation itself.
- **`cli/score.ts` no longer re-validates OLLAMA_HOST/VISION_API_STYLE.** It previously
  duplicated `visionClient.ts`'s own env rules, but more loosely — it only checked OLLAMA_HOST
  was non-empty, not that it was a well-formed URL. Given the per-record resilience added in
  the prior pass, a malformed `OLLAMA_HOST` was surfacing as N identical per-listing failures
  instead of one clear error. Added `validateVisionEnv()` to `visionClient.ts` (exported,
  reuses its existing `getOllamaHost`/`getVisionApiStyle`) and had the CLI delegate to it,
  restoring the fail-fast-before-DB-open behavior with the stricter validation.
- **Deleted `dashboard/package.json`'s fictional `main`/`types`/`exports`** — pointed at
  `./dist/index.js`, which cannot exist (dashboard has no `index.ts` anywhere, no `tsc` emit
  step; `vite build` produces client assets at a different path). Unlike `core`'s equivalent
  fields (see Escalated below), nothing imports `dashboard` by package name, so there was no
  boundary decision to make — pure noise, removed.
- **`App.tsx` now imports `RankedListing` (type-only) from `core/src/rank/rank.ts`** instead of
  hand-redeclaring a weaker `Listing`/`ListingsResponse` pair (the hand-rolled version typed
  `source` as `string` instead of the `SOURCES` union, so nothing checked it against the real
  API contract). Verified this compiles and bundles correctly via `vite build` (15 modules,
  builds clean) and passes the full Playwright e2e suite, since a client-side import reaching
  into `core/src` across the package boundary was new for this file (the dashboard *server*
  already did this; this extends the same existing pattern, not new debt).
- **[Observability] The three CLI `main().catch()` handlers logged only `err.message`,
  not the full error.** `cli/alert.ts`, `cli/score.ts`, `cli/ingest.ts` all discarded the stack
  trace on the single most severe failure path (an uncaught fatal error), and a non-`Error`
  throw rendered as `"fatal error: undefined"` (the `as Error` cast silently hid the mismatch).
  `cli/rank.ts` already logged the full error object — the other three now match.
- **[Observability] `cli/score.ts`'s `parseInputRecords()` used `process.exit(1)`** for
  empty/malformed input. This is input validation, not env validation — the one class the
  2026-08-11 pass explicitly exempted from its `process.exitCode`-not-`process.exit()`
  standardization (env checks run before any output; input checks here run after this
  function's own `console.error`, and this CLI's documented primary usage is a pipe, where a
  hard `process.exit()` risks truncating the very stderr message just written). Changed to
  `process.exitCode = 1` + return, matching the rest of the file.
- **[Observability] `dashboard/server/index.ts`'s `GET /api/listings` and
  `GET /api/listings/:id` had no error handling around their DB calls** — unlike their sibling
  `GET /api/images/:listingId`, which already logs context (the resolved file path) on failure.
  A DB-level failure on the other two routes was only visible via Hono's default handler
  (`console.error(err)` with zero request context — no listing id, no query params). Added the
  same context-logging pattern to both, returning 500 with an `{ error }` body consistent with
  the rest of the app.

## Applied — NIT

- `readAlertConfig()` (`cli/alert.ts`) no longer returns an unused `databaseUrl` field — its
  only consumer was its own presence check; the actual DB handle comes from a separate dynamic
  `import('../db/client.js')`.
- Moved `formatPriceCents`/`usdFormatter` out of `alert/buildAlert.ts` into a new, neutral
  `core/src/format.ts` — there was no domain reason for `cli/rank.ts` (a table column) or the
  dashboard client (a price cell, previously a third, independently-implemented copy of the
  same formatting logic) to depend on the alert-payload module for this.
- `score.ts`'s upsert `set` clause now derives from `listingValues` via rest-destructuring
  (excluding the three identity columns) instead of restating all seven updatable columns a
  second time — adding a new listing field can no longer silently miss one of the two lists.
- Extracted a shared `postChatAndParse()` helper in `visionClient.ts` — `callOllama` and
  `callOpenAiCompatible` were structurally identical (fetch → check `response.ok` → parse JSON
  against a Zod schema → throw on shape mismatch), differing only in endpoint path, request
  body shape, response schema, and the label used in the error message.
- Pinned quote style repo-wide: added an ESLint `quotes: ["warn", "single", { avoidEscape:
  true }]` rule (previously unenforced — style had drifted file-by-file with no formatter to
  pin it) and ran `eslint --fix` to normalize every file to single quotes (the existing
  majority).

## Escalated — not applied

  `./dist/index.js`** (no `build` script, no `src/index.ts` barrel, no `dist/`), while
  `packages/dashboard/server/index.ts` — and, as of this pass, `App.tsx` and the dashboard

  *existing* deep-relative-import pattern to two more call sites rather than introducing a new
  one — consistent with current precedent, not new debt, but doesn't resolve the underlying
  question either.
